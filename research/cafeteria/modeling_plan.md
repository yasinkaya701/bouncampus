# Cafeteria Demand Recommendation — Modeling Plan

## Decision target

The production recommendation is not a personal food recommender. The primary operational target is:

> For each campus × service date × meal type, estimate the distribution of actual served demand using only information available before the kitchen decision freeze, then select a production quantity that minimizes asymmetric surplus and shortage loss.

Menu preference is a major contextual feature, not the final target.

## Two-stage architecture

### Stage A — probabilistic demand forecast

Predict conditional demand distribution rather than a single point.

Candidate outputs:

- q10 / q50 / q90 served demand
- expected demand
- calibrated residual scale
- source coverage / readiness

Candidate models, in promotion order:

1. same-weekday / rolling median baseline
2. reservation-only baseline
3. corrected reservation baseline using historical show-rate + historical unreserved demand
4. regularized linear/Poisson/negative-binomial baseline
5. CatBoost / LightGBM / XGBoost tabular model
6. quantile gradient boosting
7. only if dataset is sufficiently long: temporal deep model

Complexity is promoted only when it beats the registered baseline on future-time common support.

### Stage B — production policy

For forecast distribution D and candidate production quantity q:

`loss(q) = surplus_weight * E[max(q - demand, 0)] + shortage_weight * E[max(demand - q, 0)]`

Weights are sensitivity parameters until operator/PMR evidence establishes real economics. They must never be described as TRY costs by default.

The production recommendation is the q minimizing expected registered loss subject to:

- kitchen capacity
- minimum batch size
- decision freeze time
- operator authority
- source-health/readiness gates

## Training row grain

One training row = one `campus_id × service_date × service_type`.

Keep package meal, breakfast, lunch and dinner as distinct service regimes. Never merge them into one demand series without a regime feature.

## Feature blocks

### 1. Calendar

- weekday
- ISO week
- month
- semester / summer regime
- instruction day
- exam period
- registration/add-drop period
- public holiday
- days since term start
- days to exam/final period

### 2. Menu

Generated by `scripts/cafeteria_labeler.py`:

- menu signature
- dish roles
- animal/plant protein mix
- explicit vegan option
- legume option
- dessert/sugary beverage counts
- known kcal coverage and summary
- portion coverage and summary
- qualitative carbon proxy
- canonical menu text

Later candidates:

- learned dish embedding
- historical residual popularity by canonical dish
- main-dish pair interaction
- novelty / time since last served

Popularity is learned from outcomes; it is never hand-labeled.

### 3. Reservation / intent

At the exact decision cutoff:

- active reservations
- cancellations before cutoff
- historical show rate using past-only rows
- corrected reservation baseline
- historical unreserved-demand level

Reservation is intent, not served demand.

### 4. Historical demand

Past-only:

- lag 1 comparable service
- lag 7 days
- rolling median/mean
- rolling dispersion
- same-weekday median
- campus × meal historical level
- previous comparable-menu residual

### 5. Weather

Use the forecast snapshot that was actually available before decision freeze, not realized weather in historical backtests:

- temperature
- precipitation probability
- precipitation amount forecast
- apparent temperature
- wind
- severe-weather indicator

Realized weather may be retained for diagnostic analysis but not silently substituted for forecast-time features.

### 6. Campus operations

If obtainable with legitimate provenance:

- class load / scheduled seat-hours
- large campus events
- dorm occupancy regime
- shuttle disruptions
- dining hall closures / capacity changes

### 7. Source health

- missing-source masks
- source freshness
- menu coverage
- reservation coverage
- weather forecast availability
- confidence/readiness state

Models must learn with missingness explicitly rather than silently dropping difficult days.

## Outcome fields

P0 required for a serious model:

- `actual_served_count`
- `prepared_count`
- `waste_kg` and/or `waste_portions`
- `active_reservations_at_cutoff`

Strongly useful:

- `reserved_served_count`
- `unreserved_served_count`
- `sellout_or_stockout`
- `service_start_at`, `service_end_at`
- operator planned production before recommendation
- operator final production after recommendation
- override reason

Item-level choice counts are optional for production-demand forecasting but are P0 if we later build per-dish choice allocation.

## Split and leakage policy

Never random-split rows across time.

Recommended evaluation:

1. expanding-window training
2. next 2–4 weeks validation
3. roll forward repeatedly
4. untouched final recent test block

All transformations using outcome history are fit inside each training window only.

Forbidden leakage examples:

- future menu popularity calculated using test-period demand
- realized weather when forecast snapshot should be used
- post-service waste as an input to same-service production decision
- reservation changes after decision cutoff
- semester/event labels created retrospectively from outcomes

## Metrics

### Forecast metrics

- MAE
- RMSE
- WAPE
- pinball loss for q10/q50/q90
- interval empirical coverage
- calibration by demand decile

### Operational metrics

- overproduction portions
- underproduction portions
- waste kg / 100 served
- stockout frequency
- registered asymmetric decision loss
- operator override rate

### Robustness slices

Report separately for:

- weekdays vs weekends
- term vs summer
- lunch vs dinner
- high vs low reservation coverage
- red-meat vs poultry vs plant menus
- rainy vs dry forecast days
- high-novelty menus
- source-missing days

## Menu effect estimation

Do not equate raw demand on a food day with food popularity. Estimate a menu effect from out-of-fold residuals after calendar, campus, reservation and weather baselines.

Example:

`menu_residual = actual_demand - baseline_without_menu_prediction`

Then estimate dish-level residual effects with shrinkage:

- require minimum historical support
- shrink low-n dishes toward zero
- distinguish main vs side positions
- avoid assigning all service residual to every item equally

This produces a defensible learned popularity signal rather than intuition labels.

## Cold start

For a new dish:

1. use semantic/name/category features
2. use protein/preparation/role family prior
3. borrow from similar dishes
4. high uncertainty until observed repeatedly

Do not invent a popularity score.

## Candidate serious model

Once at least several hundred trustworthy service rows exist:

- CatBoost median model for q50
- CatBoost/LightGBM quantile models for q10/q90
- categorical inputs: campus, meal, weekday, menu categories
- numeric inputs: reservations, lags, weather, calendar intensity, menu aggregates
- text/embedding experiment only after tabular baseline is stable
- conformal or empirical residual calibration on rolling validation if interval validity improves

Why tree boosting first: cafeteria demand is tabular, nonlinear and interaction-heavy, while available history is likely much smaller than what a deep temporal model needs.

## Scientific support

Relevant external evidence includes:

- Faezirad, Pooya & Naji-Azimi (2021), *Preventing food waste in subsidy-based university dining systems: An artificial neural network-aided model under uncertainty*. Uses reservation/no-show behavior and optimizes under shortage/waste cost uncertainty.
- Santos & Gomide (2026), *Evaluating the Effectiveness and Impact of Machine Learning Models for Forecasting Meal Demand in University Restaurants*. Evaluates Decision Tree, XGBoost and LSTM on historical consumption, holidays and menu attributes; reports menu information as useful and XGBoost as strongest in that case study.

These papers motivate candidate experiments; their reported performance is not evidence that BOUNCAMPUS will achieve the same results.

## Promotion gates

No model is called production-ready unless all are true:

1. target data is measured and reconciled
2. no future leakage found
3. future-time benchmark beats registered operational baseline
4. gains persist on relevant slices
5. uncertainty behavior is evaluated
6. decision policy is better under registered loss, not just lower RMSE
7. source missingness fails safely
8. recommendation remains human-approved

Until these gates pass, outputs remain offline benchmark / shadow recommendation evidence.
